# R9 Production Deployment Runbook

**Scope:** Render production topology and configuration for the MedFlow backend, durable malware recovery worker, patient app, doctor portal, and admin portal.

This runbook describes the deployment contract represented by `render.yaml`. It does **not** record an executed production deployment. A production release is complete only after the Blueprint has been applied to the target Render workspace, secrets have been provisioned, the private ClamAV dependency is reachable, migrations have succeeded, and post-deploy verification has passed.

## 1. Production Topology

The Blueprint defines five MedFlow services:

- `medflow-backend-prod`: Python web service running FastAPI/Uvicorn.
- `medflow-malware-worker-prod`: Python background worker running `python -m app.workers.malware_worker` for durable recovery of pending malware scans.
- `medflow-patient-app-prod`: Vite static site.
- `medflow-doctor-portal-prod`: Vite static site.
- `medflow-admin-portal-prod`: Vite static site.

The ClamAV daemon is a separate, network-restricted production dependency addressed through `CLAMAV_HOST`. The Blueprint deliberately does not invent a public scanner service. The scanner must be provisioned on infrastructure reachable by the backend and malware worker and must not be exposed as a browser-facing service.

The three browser applications receive the backend public URL through `VITE_API_BASE_URL`. Patient and doctor WebSocket clients derive `ws://`/`wss://` from the same backend base URL and connect only to `/ws` using the authenticated subprotocol flow.

Deployments use `autoDeployTrigger: checksPass`. Alembic migrations execute only in the backend `preDeployCommand`, not in the build step or malware worker. The backend readiness endpoint is `/ready`.

## 2. Required Production Configuration

Before the first backend/worker deploy, provision these values in Render:

| Variable | Requirement |
| --- | --- |
| `DATABASE_URL` | Production PostgreSQL connection string. SQLite is rejected. Required by backend and malware worker. |
| `SUPABASE_URL` | Production Supabase project URL. Required by backend and malware worker. |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only Supabase service-role credential. Never expose it to a Vite/static-site environment variable. Required by backend and malware worker. |
| `SUPABASE_STORAGE_BUCKET` | Private medical-document bucket; Blueprint default is `medical-documents`. |
| `ENCRYPTION_KEY` | Stable Fernet key used by the **web** role for encrypted MFA secrets. Back it up securely; changing it without a migration makes previously encrypted secrets unreadable. |
| `SECRET_KEY` | Generated by Render for the **web** role. Treat it as stable after initial creation; rotation invalidates existing JWTs. |
| `CLAMAV_HOST` | Private/restricted hostname or IP for the production ClamAV daemon. Required by both backend and malware worker. |
| `CLAMAV_PORT` | Scanner TCP port; Blueprint default `3310`. |
| `CLAMAV_TIMEOUT_SECONDS` | Scanner socket timeout; worker Blueprint default `15`. |
| `CLAMAV_MAX_BYTES` | Maximum payload accepted by the scanner client; worker Blueprint default `10485760` bytes. |
| `MALWARE_WORKER_BATCH_SIZE` | Maximum pending document IDs processed per worker discovery batch; default `25`. |
| `MALWARE_WORKER_POLL_SECONDS` | Worker idle polling interval; default `5`. |
| `TRUSTED_PROXY_CIDRS` | Only actual trusted ingress/reverse-proxy networks. Leave empty if the trust boundary is unknown. Invalid entries and catch-all networks such as `0.0.0.0/0` are rejected. |
| `FRONTEND_CORS_ORIGINS` | Optional comma-separated custom frontend origins in addition to Render-generated service origins. Wildcards are rejected; production origins must use HTTPS. |
| `REFRESH_COOKIE_SAMESITE` | Blueprint value `none`. Production cookies are also forced `Secure` and `HttpOnly`. |
| `MEDFLOW_SERVICE_ROLE` | Blueprint-managed process role: `web` for the backend or `malware_worker` for the recovery worker. Do not override manually. |

The Blueprint derives `PATIENT_APP_ORIGIN`, `DOCTOR_PORTAL_ORIGIN`, and `ADMIN_PORTAL_ORIGIN` from the deployed static-service public URLs. The web role fails startup in production if no explicit HTTPS browser origin is available.

The malware worker intentionally does not receive `SECRET_KEY`, `ENCRYPTION_KEY`, or browser CORS settings because it does not issue JWTs, decrypt MFA material, or serve browser traffic. This reduces secret exposure across process roles.

## 3. Browser, Header, Cookie, and WebSocket Boundary

The static applications and API are separate browser origins. Credentialed CORS therefore uses an exact allowlist and never `*`. The backend also restricts CORS to the HTTP methods and request headers used by MedFlow clients.

Production API documentation surfaces (`/docs`, `/redoc`, `/openapi.json`) are disabled. Backend responses carry HSTS, an API-only CSP, anti-framing/nosniff controls, no-referrer and restrictive permissions policies, and `Cache-Control: no-store`/`Pragma: no-cache` to reduce PHI caching in browsers and intermediaries.

Each Render static site sets its own HSTS, CSP, anti-framing/nosniff, no-referrer, and restrictive permissions headers. Fingerprinted `/assets/*` resources use immutable long-lived caching; the SPA HTML continues to use normal hosting cache behavior so releases are not pinned to stale shell HTML.

Production refresh cookies use `HttpOnly; Secure; SameSite=None` so the cookie can accompany credentialed requests to the API when frontend and backend are on separate sites. Because `SameSite=None` removes the browser's Lax CSRF barrier, `/api/auth/refresh` and `/api/auth/logout` validate any browser `Origin` header against the same explicit frontend allowlist before using the cookie.

For a long-lived public production deployment, use custom domains under an organization-controlled parent domain when possible. When adding custom frontend domains, add their exact HTTPS origins to `FRONTEND_CORS_ORIGINS` and redeploy the backend.

Patient and doctor realtime clients derive their WebSocket target from `VITE_API_BASE_URL`, promote HTTPS to WSS, clear query parameters, and authenticate through the `medflow.jwt` subprotocol flow. JWTs must never be placed in a WebSocket URL.

## 4. Pre-Deployment Gate

Before syncing or deploying the Blueprint:

1. Confirm the release commit has passed the GitHub Actions backend job and all three frontend lint/test/build jobs, including the P3 production-hardening regression stage.
2. Confirm `alembic heads` reports a single migration head and the CI migration round-trip/schema-drift gate is green.
3. Confirm a restorable PostgreSQL/Supabase database backup/PITR point exists according to `PRODUCTION_MIGRATION_RUNBOOK.md`.
4. Confirm the production storage bucket is private and both backend and worker have the required server-side Supabase credential.
5. Provision a private/restricted ClamAV daemon and verify both backend and malware worker can reach `CLAMAV_HOST:CLAMAV_PORT`.
6. Confirm `TRUSTED_PROXY_CIDRS` contains only known ingress networks and never a catch-all network.
7. Confirm every `sync: false` Render variable is populated before traffic is accepted.
8. Confirm the release branch is protected by repository rules requiring CI checks and preventing unreviewed/unchecked changes.

Do not copy development `.env` values into production.

## 5. Blueprint Deployment Sequence

1. Merge the verified release to the production branch used by the Render Blueprint.
2. Create or sync the Blueprint from repository-root `render.yaml`.
3. Populate every `sync: false` variable before accepting a production release.
4. Verify Render resolves the three static-service `RENDER_EXTERNAL_URL` values into backend origin variables and the backend URL into every frontend `VITE_API_BASE_URL` build.
5. Allow the backend build to complete; Alembic then runs as the backend pre-deploy command. A migration failure must block activation of the new backend release.
6. Start the malware worker only after database/storage/scanner configuration is present. It must not run migrations.
7. Allow the three Vite static-site builds to complete using `npm ci`.
8. Do not treat a successful build alone as a successful production release; execute the verification section below.

## 6. Post-Deployment Verification

Verify against deployed production URLs without bypassing public ingress for browser/API checks:

1. `GET /health` returns the backend liveness response and `GET /ready` confirms database readiness.
2. Confirm `/docs`, `/redoc`, and `/openapi.json` are not exposed in production.
3. Inspect backend response headers and confirm HSTS, CSP, no-referrer, no-store, nosniff, anti-framing, and permissions restrictions are present.
4. Open each frontend by root and at least one deep React Router URL; the SPA rewrite must return the app rather than a static 404. Confirm the static security headers are present.
5. Log in through each applicable portal and verify authenticated `/api/auth/me` succeeds.
6. Verify a refresh cycle succeeds and inspect refresh cookie attributes: `HttpOnly`, `Secure`, and the configured `SameSite` value.
7. Verify an untrusted browser origin cannot use refresh/logout cookie endpoints and an untrusted CORS method/header preflight is rejected.
8. From patient and doctor portals, establish WSS to `/ws` and confirm the bearer is absent from the URL.
9. Upload a benign test document and confirm it progresses from `pending` to `clean` through the configured ClamAV path before release.
10. Run the inert EICAR antivirus test signature through an approved non-production/verification path and confirm it is classified malicious and remains unreleasable. Never use EICAR in a real patient record.
11. Stop/restart a web process with a persisted `pending` test upload and verify the dedicated malware worker recovers the pending scan.
12. Exercise the MedFlow golden workflow for consent-protected data access and revocation.
13. Verify unauthorized cross-patient/cross-organization attempts still fail closed.
14. Check backend and worker logs for migration errors, repeated authentication failures, CORS failures, scan errors, long-lived pending documents, or storage/scanner connectivity failures.

Record the exact deployed commit SHA, Render deploy IDs, URLs, migration output, scanner/worker verification evidence, and smoke-test evidence in the production release record.

## 7. Rollback

Application rollback and database rollback are separate decisions.

- If application code is faulty but the migration is backward-compatible, roll the Render services back to the last verified deploy and retain the additive schema.
- If a destructive or incompatible migration has corrupted production behavior, follow `PRODUCTION_MIGRATION_RUNBOOK.md` and restore from the verified database backup/PITR point. Do not assume `alembic downgrade` is safe for destructive production recovery.
- If the malware worker is faulty, stop the worker; documents remain fail-closed in `pending`/`scan_error` rather than being released unscanned. Restore a verified worker release before reprocessing pending records.
- If ClamAV is unavailable, uploads/download release remain fail-closed. Repair scanner connectivity before manually requeueing affected `scan_error` records.
- If a secret was exposed, rotate the affected secret rather than only rolling back code. `SECRET_KEY` rotation invalidates issued JWTs; `ENCRYPTION_KEY` rotation requires an explicit re-encryption migration for stored MFA material.
- After rollback, rerun `/health`, `/ready`, login/refresh, WebSocket, malware scan, and consent-protected golden-flow checks.

## 8. Remaining External Operations Evidence

The repository now defines the durable malware recovery worker and its production scanner contract, but it does not create or certify a particular ClamAV infrastructure provider. Operations must provision the private scanner, monitoring, alerting, and network policy in the target environment.

Likewise, this runbook does not claim penetration testing, disaster-recovery exercise completion, regulatory certification, or overall production-readiness sign-off. Repository branch/ruleset protection is an account-level GitHub administration control and must be verified in the repository settings before a production release.
