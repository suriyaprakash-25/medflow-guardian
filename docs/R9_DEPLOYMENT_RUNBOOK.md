# R9 Production Deployment Runbook

**Scope:** Render production topology and configuration for the MedFlow backend, patient app, doctor portal, and admin portal.

This runbook describes the deployment contract represented by `render.yaml`. It does **not** record an executed production deployment. A production release is complete only after the Blueprint has been applied to the target Render workspace, secrets have been provisioned, migrations have succeeded, and post-deploy verification has passed.

## 1. Production Topology

The Blueprint defines four public services:

- `medflow-backend-prod`: Python web service running FastAPI/Uvicorn.
- `medflow-patient-app-prod`: Vite static site.
- `medflow-doctor-portal-prod`: Vite static site.
- `medflow-admin-portal-prod`: Vite static site.

The three browser applications receive the backend public URL through `VITE_API_BASE_URL`. Patient and doctor WebSocket clients derive `ws://`/`wss://` from the same backend base URL and connect only to `/ws` using the R8 authenticated subprotocol protocol.

Deployments use `autoDeployTrigger: checksPass`. Alembic migrations execute in the backend `preDeployCommand`, not in the image/build step. The backend readiness endpoint is `/ready`.

## 2. Required Production Configuration

Before the first backend deploy, provision these values in Render:

| Variable | Requirement |
| --- | --- |
| `DATABASE_URL` | Production PostgreSQL connection string. For the current architecture this is the Supabase PostgreSQL database; SQLite is rejected. |
| `SUPABASE_URL` | Production Supabase project URL. |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only Supabase service-role credential. Never expose it to a Vite/static-site environment variable. |
| `SUPABASE_STORAGE_BUCKET` | Private medical-document bucket; Blueprint default is `medical-documents`. |
| `ENCRYPTION_KEY` | Stable Fernet key used for encrypted MFA secrets. Back it up securely; changing it without a migration makes previously encrypted secrets unreadable. |
| `SECRET_KEY` | Generated by Render for a new Blueprint service. Treat it as stable after initial creation; rotation invalidates existing JWTs. |
| `TRUSTED_PROXY_CIDRS` | Only the actual trusted ingress/reverse-proxy networks. Leave empty if the trust boundary is not known; this safely ignores `X-Forwarded-For`. Never use `0.0.0.0/0`. |
| `FRONTEND_CORS_ORIGINS` | Optional comma-separated custom frontend origins in addition to the Render-generated service origins. No wildcard is accepted. |
| `REFRESH_COOKIE_SAMESITE` | Blueprint value `none`. Production cookies are also forced `Secure` and `HttpOnly`. |

The Blueprint derives `PATIENT_APP_ORIGIN`, `DOCTOR_PORTAL_ORIGIN`, and `ADMIN_PORTAL_ORIGIN` from the deployed static-service public URLs. The backend fails startup in production if no explicit browser origin is available.

## 3. Browser Origin, Cookie, and WebSocket Boundary

The static applications and API are separate browser origins. Credentialed CORS therefore uses an exact allowlist and never `*`.

Production refresh cookies use `HttpOnly; Secure; SameSite=None` so the cookie can accompany credentialed requests to the API when frontend and backend are on separate sites. Because `SameSite=None` removes the browser's Lax CSRF barrier, `/api/auth/refresh` and `/api/auth/logout` validate any browser `Origin` header against the same explicit frontend allowlist before using the cookie.

For a long-lived public production deployment, use custom domains under an organization-controlled domain when possible (for example, separate patient/doctor/admin/API hosts under the same owned parent domain). This reduces dependence on third-party-cookie behavior across hosting-provider tenant domains. When adding custom frontend domains, add their exact origins to `FRONTEND_CORS_ORIGINS` and redeploy the backend.

Patient and doctor realtime clients derive their WebSocket target from `VITE_API_BASE_URL`, promote HTTPS to WSS, clear query parameters, and authenticate through the R8 `medflow.jwt` subprotocol flow. JWTs must never be placed in a WebSocket URL.

## 4. Pre-Deployment Gate

Before syncing or deploying the Blueprint:

1. Confirm the release commit has passed the GitHub Actions backend job and all three frontend builds.
2. Confirm the targeted R9 deployment configuration tests pass.
3. Confirm `alembic heads` reports a single migration head.
4. Confirm a restorable Supabase database backup/PITR point exists according to `PRODUCTION_MIGRATION_RUNBOOK.md`.
5. Confirm the production storage bucket is private and the backend has the required server-side Supabase credential.
6. Confirm all manual Render environment variables above are populated before the backend is allowed to serve traffic.

Do not copy development `.env` values into production.

## 5. Blueprint Deployment Sequence

1. Merge the verified release to the production branch used by the Render Blueprint.
2. Create or sync the Blueprint from the repository root `render.yaml`.
3. Populate every `sync: false` variable before accepting a production release.
4. Verify Render resolves the three static-service `RENDER_EXTERNAL_URL` values into the backend origin variables and the backend `RENDER_EXTERNAL_URL` into every frontend `VITE_API_BASE_URL` build.
5. Allow the backend build to complete. Alembic then runs as the pre-deploy command. A migration failure must block activation of the new backend release.
6. Allow the three Vite static-site builds to complete using `npm ci`.
7. Do not treat a successful build alone as a successful production release; execute the verification section below.

## 6. Post-Deployment Verification

Verify against the deployed production URLs, without bypassing the public ingress path:

1. `GET /health` returns the backend liveness response.
2. `GET /ready` succeeds and confirms database readiness.
3. Open each frontend by its root URL and by at least one deep React Router URL; the SPA rewrite must return the application rather than a static 404.
4. Log in through each applicable portal and verify authenticated `/api/auth/me` succeeds.
5. Verify a refresh cycle succeeds after the short access-token lifecycle begins, and inspect the refresh cookie attributes: `HttpOnly`, `Secure`, and the configured `SameSite` value.
6. Verify an untrusted browser origin cannot use the refresh/logout cookie endpoints.
7. From patient and doctor portals, establish a WSS connection to backend `/ws` and confirm the bearer is absent from the URL.
8. Exercise the MedFlow golden workflow for consent-protected data access and revocation.
9. Verify unauthorized cross-patient/cross-organization attempts still fail closed.
10. Check backend logs for migration errors, repeated authentication failures, unexpected CORS failures, or storage connectivity failures.

Record the exact deployed commit SHA, Render deploy IDs, URLs, migration output, and smoke-test evidence in the production release record.

## 7. Rollback

Application rollback and database rollback are separate decisions.

- If application code is faulty but the migration is backward-compatible, roll the Render services back to the last verified deploy and retain the additive schema.
- If a destructive or incompatible migration has corrupted production behavior, follow `PRODUCTION_MIGRATION_RUNBOOK.md` and restore from the verified Supabase backup/PITR point. Do not assume `alembic downgrade` is safe for destructive production recovery.
- If a secret was exposed, rotate the affected secret rather than only rolling back code. `SECRET_KEY` rotation invalidates issued JWTs; `ENCRYPTION_KEY` rotation requires an explicit re-encryption migration for stored MFA material.
- After rollback, rerun `/health`, `/ready`, login/refresh, WebSocket, and consent-protected golden-flow checks.

## 8. Deliberately Deferred Infrastructure

The current `dev` integration branch does not yet include the complete R7 malware-scanner worker deployment. R9 therefore does not invent a ClamAV worker command or claim malware-scanner production availability. When the verified R7 implementation is integrated, its private scanner service, worker lifecycle, recovery behavior, credentials, monitoring, and deployment health checks must be added as a separate verified infrastructure change.

Likewise, this runbook does not claim penetration testing, disaster-recovery exercise completion, regulatory certification, or overall production-readiness sign-off. Those require their own evidence gates.
