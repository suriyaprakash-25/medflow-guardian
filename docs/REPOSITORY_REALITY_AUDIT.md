# MedFlow Guardian Repository Reality Audit

## 1. Executive Summary
The MedFlow Guardian repository contains a partially functional but highly simplified prototype. The architecture currently acts as a traditional role-based application. The core requirement of "Consent as an authoritative versioned policy" and "Enforcement-state verification" does NOT exist in the codebase. Supabase PostgreSQL and Storage are integrated, but advanced authorization logic is missing.

## 2. Current Repository Structure
- `/patient-app`: React 18, Vite, Tailwind CSS, TypeScript
- `/doctor-portal`: React 18, Vite, Tailwind CSS, TypeScript
- `/backend`: FastAPI, SQLAlchemy, Alembic, Uvicorn, Pytest
- `/docs`: Architecture, migration, and context documentation
- `/frontend-shared`: Empty or missing shared component implementations
- `/backend/scripts`: Database utilities and cleanup scripts

## 3. Current Frontend Architecture
- **Framework**: React 18 with Vite.
- **Routing**: `react-router-dom` v7.
- **Styling**: Tailwind CSS.
- **Auth Flow**: Simple local storage JWT `localStorage.getItem('token')`.
- **State**: Basic React hooks, no complex state management (Redux/Zustand).

## 4. Current Backend Architecture
- **Framework**: FastAPI (Python 3.11).
- **ORM**: SQLAlchemy.
- **Auth**: JWT via `jose`.
- **Realtime**: WebSockets using FastAPI `WebSocket` classes.
- **Modularity**: Separated by routers (auth, triage, access, documents).

## 5. Current Database Architecture
- **Engine**: Supabase PostgreSQL.
- **Migration**: Alembic used for schema definitions.
- **Models**: `User`, `Hospital`, `HospitalStaff`, `MedicalDocument`, `DocumentAccessRequest`, `DocumentAccessGrant`, `TriageRequest`, `AuditLog`.

## 6. Current Storage Architecture
- **Storage**: Supabase Storage (`storage3` Python client).
- **Access**: Signed URLs generated server-side.
- **Security**: Bucket is marked private. Backend uses Service Role Key.

## 7. Current Authentication Architecture
- **Type**: Local JWT (not external OIDC like Auth0).
- **Storage**: Tokens generated by FastAPI, stored in `localStorage` on frontend.
- **Missing**: Refresh tokens, logout invalidation, OIDC integration.

## 8. Current Authorization Architecture
- **Type**: Simple Role-Based Access Control (RBAC).
- **Missing**: Contextual Policy Engine, Consent State verification.

## 9. Current Organization/Hospital Model
- **Entities**: `Hospital`, `HospitalStaff`.
- **Isolation**: Handled via simple SQL joins matching user IDs to `HospitalStaff`. Not fully abstracted or strictly bounded at the middleware layer.

## 10. Current Consent Architecture
- **Status**: MISSING.
- **Reality**: There is no `Consent`, `ConsentPolicy`, or `ConsentState` model in `app/models`. Access is handled directly via `DocumentAccessGrant` requests.

## 11. Current Policy Architecture
- **Status**: MISSING.
- **Reality**: No rules engine, no evaluated contexts.

## 12. Current Enforcement Architecture
- **Status**: MISSING.
- **Reality**: Standard REST route checks, no generic "Enforcement Point" decoupling.

## 13. Enforcement-state verification status
- **Status**: MISSING.
- **Reality**: "Stale authorization" bypass prevention is entirely absent.

## 14. Document Security
- **Uploads**: Authenticated endpoint uploads to Supabase.
- **Downloads**: Generates a pre-signed URL after checking `DocumentAccessGrant`.
- **Risks**: Expiration handles access, but dynamic revocation does not invalidate pre-signed URLs immediately.

## 15. WebSocket Security
- **Authentication**: Validates JWT token on connection (`verify_token`).
- **Isolation**: Handled manually per endpoint, tracks `hospital_ids`.
- **Risks**: Potential race conditions and weak subscriptions.

## 16. Audit Architecture
- **Status**: PARTIAL.
- **Reality**: An `AuditLog` model exists, but lacks correlation IDs, consent states, and fine-grained "Enforcement" context.

## 19. Deployment Status
- **Status**: MISSING / LOCAL ONLY.
- **Reality**: No Dockerfile, `docker-compose.yml`, or CI/CD pipelines configured for production deployment.

## 20. Configuration/Secrets
- `.env` usage in backend for JWT secrets and Supabase keys.
- **Risk**: `.env.example` exists. Secrets are strictly backend.

## 21. Code Quality
- Clean, modular backend.
- Missing shared frontend logic.
- Hardcoded base URLs in API clients (`http://localhost:8000`).

## 22. Production Readiness Score
- **Score**: 35/100
- **Reason**: Database and Storage are functional, but the entire architectural premise (Consent as Policy, Stale Enforcement Prevention) is missing.

## 23. P0 findings
- **Consent Architecture completely missing**.
- **Enforcement State Verification completely missing**.

## 24. P1 findings
- **Stale Authorization Bypass**: If a grant is revoked, previously generated signed URLs might still be valid for their duration.
- **Authentication**: Local JWT without refresh tokens, invalidation, or Auth0 integration.

## 25. P2 findings
- **Missing Deployment Infrastructure**.
- **No API Rate Limiting**.

## 26. P3 findings
- Hardcoded frontend API endpoints.
- Incomplete audit trails.

## 27. Architecture discrepancies
- **Design**: OIDC/Auth0 identity. **Reality**: Local JWT.
- **Design**: Consent Policies & States. **Reality**: Direct Access Grants only.
- **Design**: NestJS + Prisma. **Reality**: FastAPI + SQLAlchemy.

## 28. Missing capabilities
- State Divergence Detection.
- OIDC Authentication.
- Consent Versioning.

## 29. Recommended implementation order
1. Implement Consent State and Policy Engine models in SQLAlchemy.
2. Integrate contextual Authorization enforcement middleware.
3. Replace local JWT with OIDC/Auth0 if strictly required, or solidify local JWT.
4. Update Document and Access request flows to check Enforcement State vs Authoritative Consent.
